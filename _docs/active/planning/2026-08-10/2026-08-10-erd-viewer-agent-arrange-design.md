# 에이전트가 배치를 시키게 하기 — `erd plan` / `erd arrange` 설계

- 상태: planning
- 토픽: `erd-viewer`
- 작성: 2026-08-10
- 작업 표면: `frontend/packages/cli` (기하 상수는 `erd-core`)

## 문제

다른 AI 에이전트가 남의 저장소에서 `npx crowfoot`으로 **읽을 만한 ERD**를 만들게 하고 싶다.
읽을 만하다는 것은 곧 **같은 맥락끼리 묶여 있고, 겹치지 않고, 설명이 붙어 있다**는 뜻이다.

지금은 두 가지가 막는다.

### ① 문서가 패키지에 안 실린다

```json
"files": ["dist-cli/**/*", "LICENSE", "NOTICE"]
```

`docs/usage.md`는 이 저장소에만 있다. 남의 저장소에 있는 에이전트가 볼 수 있는 것은
`--help`와 npm README(npm이 자동 포함)뿐이다.

### ② 배치는 에이전트가 하기 나쁜 일이다

`layout.json`을 직접 쓰려면 아래를 전부 알아야 하고, **넷 다 틀려도 다이어그램은 그려진다.**
조용히 잘못 그려질 뿐이다.

| 알아야 하는 것 | 지금 어디 있나 |
|---|---|
| 노드 크기 = `52 + 컬럼수 × 34`, 폭 340 | `demo/build-demo.mjs` 주석. **CSS에서 눈으로 잰 값** |
| 그룹 박스는 멤버 바운드에서 파생되고 사방에 `GROUP_BOX_PADDING`(24)이 붙는다 → 두 그룹 간격이 48 미만이면 박스가 겹친다 | `group/groupNode.ts` |
| **관계가 없는 테이블은 `parentId`가 붙는다** | `convertSchemaToNodes.ts:63` |
| 메모는 넘치면 조용히 잘린다 (`overflow: hidden`, `scrollHeight`도 잘린 값을 보고) | `demo/README.md` 함정 ③ |

세 번째는 데모 README에 "뷰어가 `layout.json`을 무시한다"고 적어뒀는데 **정확하지 않다.**
무시하는 게 아니라, `parentId`가 붙은 노드의 좌표를 React Flow가 **부모 상대로 해석**한다.
같은 숫자가 다른 좌표계에서 읽히는 것이다. 문서도 같이 고친다.

## 역할 분담

이 설계의 전제 한 줄.

> **에이전트는 의미를 정하고, CLI는 기하를 책임진다.**

어떤 테이블이 한 맥락인지 판단하는 것은 에이전트가 잘한다 — 그리고 좌표가 전혀 필요 없다.
위 표의 넷은 전부 재유도하면 틀리는 물리 상수다. 그래서 **함정을 설명하는 매뉴얼이 아니라
함정을 없애는 명령**으로 간다.

## 결정

| 질문 | 결정 | 근거 |
|---|---|---|
| 매뉴얼인가 명령인가 | **명령.** 매뉴얼은 그 부산물 | 매뉴얼로 쓸 내용의 대부분이 "틀리면 조용히 잘못 그려지는 상수"다 |
| 범위 | **`erd arrange` + `erd plan`** | 에이전트가 빈 종이에서 시작하지 않는다. 테이블명 누락·오타가 구조적으로 불가능해진다 |
| 뼈대가 그룹을 제안하나 | **한다. ~~FK 연결요소~~ → 이름 접두사 기준** | 결정론적이라 환각이 아니다. **FK 연결요소는 구현 후 실제 스키마에서 무너졌다** — 아래 참고 |
| 좌표를 에이전트가 쓰나 | **한 번도 안 쓴다** | `plan.json`에 좌표 필드 자체를 두지 않는다 |

## 워크플로

```bash
npx crowfoot erd build   --input schema.sql --format postgres --output-dir dist
npx crowfoot erd plan    --input dist/schema.json > plan.json
#   에이전트가 plan.json 의 그룹 이름 · 소속 · 색 · 메모 문구만 고친다
npx crowfoot erd arrange --input dist/schema.json --plan plan.json --output-dir dist
```

`arrange`가 `layout.json` · `groups.json` · `memos.json` 세 개를 쓴다. 기존
`from-link`와 출력이 같은 자리라, 뒤에 붙는 배포 절차는 바뀌지 않는다.

## `plan.json`

**좌표 필드가 없다.** 이것이 형식의 전부다.

```json
{
  "groups": [
    { "id": "vocab", "name": "Vocabulary", "color": "sky",
      "tables": ["words", "word_examples", "wordbooks"] }
  ],
  "memos": [
    { "text": "여기부터 어휘 도메인", "color": "vermilion", "fontSize": 40, "span": 2 }
  ]
}
```

- `color` — 기존 12색 팔레트 키. 팔레트 밖이면 **에러로 멈춘다**(뷰어는 조용히 버린다).
- `memos` — 다이어그램 위쪽 띠에 순서대로 놓이고 열 수만큼 줄바꿈된다. `span`은 열 단위 폭.
  **크기는 `arrange`가 본문에서 계산한다** — 이것이 함정 ③을 없애는 방식.
- 계획에 없는 테이블은 그룹 밖으로 배치된다. 스키마에 없는 이름은 **에러**.

## `arrange`가 책임지는 것

| 함정 | 처리 |
|---|---|
| 노드 크기 | 스키마의 컬럼 수에서 계산. 상수는 `erd-core`가 소유하고 CLI가 가져다 쓴다 |
| 그룹 박스 겹침 | 그룹 간 최소 간격을 `GROUP_BOX_PADDING * 2`에서 **유도**한다. 데모의 340 같은 눈대중 숫자를 CLI가 들고 있지 않는다 |
| 관계 없는 테이블 | `layout.json`에 **쓰지 않는다.** 좌표계가 다르므로 쓰면 틀린다. 대신 stdout에 "이 테이블들은 뷰어가 자체 그룹에 배치한다"고 알린다 |
| 메모 잘림 | 본문 줄 수와 폰트 크기에서 높이를, 최장 줄에서 폭을 잡는다 |

## 검수 기준

**`demo/build-demo.mjs`가 이 명령의 하드코딩 버전이다.** `arrange`가 현재 데모 배치를
재현할 수 있어야 한다. 재현되면 그 스크립트는 `demo/plan.json` 하나로 줄고, **데모가 곧 이
기능의 인수 테스트가 된다.**

- 단위: 패킹(그룹 n개 × 테이블 m개에서 어떤 두 박스도 안 겹침) · 메모 크기 · 팔레트 검증 ·
  없는 테이블명 에러 · 연결요소 계산
- 통합: 데모 스키마 + `demo/plan.json` → 생성된 `layout.json`을 현재 커밋된 것과 비교
- 브라우저: 생성 결과를 띄워 **그룹 박스 쌍끼리 겹침 0**, **메모 `scrollHeight` 잘림 0**
  (이미 쓰는 측정 방식 그대로)

## 상수 드리프트 방어

노드 폭 340 · 헤더 52 · 행 34는 **CSS에서 눈으로 잰 값**이다. 테이블 스타일이 바뀌면 CLI가
조용히 어긋난 배치를 만든다. `erd-core`에 **렌더된 테이블의 실측 크기가 이 상수와 같은지
확인하는 테스트**를 둔다. 드리프트를 조용한 오배치가 아니라 실패하는 테스트로 바꾼다.

## 매뉴얼 (부산물)

1. **npm README에 "For AI agents" 절** — 패키지와 함께 실리는 유일한 문서다. 위 3줄
   워크플로와 `plan.json` 예시.
2. `--help` — `plan`은 뼈대를, `arrange`는 무엇을 계산해주는지.
3. `docs/usage.md` · `usage_en.md`에 절 추가.

별도 `crowfoot agents` 명령은 만들지 않는다. 뼈대 자체가 형식을 설명한다.

## 열린 질문

- **관계 없는 테이블이 있을 때 그룹들을 어디서 시작할 것인가.** 데모는 `X0 = 3100`을
  눈대중으로 박았다. 뷰어의 자체 그룹이 어디에 놓이는지는 ELK가 정하므로 CLI가 미리 알 수
  없다. 후보: ① 자체 그룹 크기를 테이블 수에서 추정해 오프셋 계산 ② 오프셋을 두지 않고
  겹치면 사용자가 `Tidy up` ③ `arrange`가 경고만. **구현 전 실측 필요** — 이 설계에서 가장
  불확실한 지점이다.
- `erd build`가 `plan.json`이 있으면 자동으로 `arrange`까지 할 것인가. 명령이 하나로 줄지만
  마법이 늘어난다.

## 범위 밖

MCP 서버 · 에이전트가 스키마를 *편집*하는 경로 · 그룹 자동 명명(이름은 에이전트가 정한다).

## 곁가지로 발견한 것

루트 `AGENTS.md`는 **이 저장소에 기여하는 법**이고 CLI 사용법이 아니다. 게다가 릴리스 절차가
`pnpm release`(빌드 + `npm publish`)라고 적혀 있는데, 실제로는 태그로 게이트되는 CI다.
이 작업과 별개로 고쳐야 한다.

## 구현 후 정정 (2026-08-11)

**FK 연결요소 기준은 틀렸다.** 사내 carbon 백엔드(77테이블 / 131 FK)에 돌려보니
`1 group(s) suggested` — 74개가 전부 한 덩어리로 나왔다.

원인은 허브 테이블이다. 그 스키마에서 `users`의 FK degree가 **32**다. 실무 애플리케이션
스키마는 어딘가에서 전부 이어져 있으므로 연결요소가 갈리지 않는다. 23테이블 데모에서 13개
섬이 나온 것은 그 스키마가 우연히 끊겨 있었기 때문이고, 그걸 근거로 삼은 것이 실수였다.

**이름 접두사로 교체했다.** 같은 스키마에서 11개 그룹 / 54테이블로 갈린다:
`estimate_*`(15) `template_*`(11) `parsing_*`(6) `formula_*` `mail_*` `project_*`(각 4) 등.
테이블은 자기가 속한 것의 이름을 따르기 때문이고, 접두사가 하나뿐인 테이블은 묶지 않는다.

같은 실측에서 두 번째 결함도 나왔다: **모든 블록이 2열 고정이라 큰 블록이 리본이 됐다.**
15개짜리 `estimate_*`가 8단으로 쌓여 다이어그램 전체 높이를 정했다. 블록 크기에 따라 열
수를 늘리고(열당 5개, 최대 4열) 가장 짧은 열에 채우도록 바꾸니 **높이 4654 → 2586 (−44%)**,
폭은 11% 증가. 겹침은 여전히 0.

두 결함 모두 **큰 실제 스키마에서만 드러났다.** 데모 스키마로는 둘 다 통과했다.
