# 큰 스키마에서 한 곳만 보기 — 포커스 모드 설계

- 상태: planning
- 토픽: `erd-viewer`
- 작성: 2026-08-09
- 작업 표면: `frontend/packages/erd-core`

## 문제

테이블이 100개를 넘으면 두 가지가 동시에 무너진다.

**읽을 수가 없다.** 116개 테이블과 154개 관계선이 한 화면에 있으면 특정 테이블이 무엇과
이어져 있는지 눈으로 좇는 것이 불가능하다. 유료 도구 중 Azimutt이 정확히 이 지점을
차별점으로 판다 — 수백 개짜리 실무 스키마를 탐색·필터링·추적하게 해주는 것.

**느리다.** 이미 측정해 둔 결론: 비용은 스키마 계층이 아니라 **테이블마다 붙는 Radix
tooltip·context-menu 기계**에 있다(`TooltipProvider` 인스턴스 1,096개 / 1,618ms).

두 문제의 해법이 같다는 것이 이 설계의 근거다. React Flow의 노드 래퍼는

```js
if (node.hidden) { return null }   // @xyflow/react 12.8.6, edge도 동일
```

이라서, **숨긴 테이블은 DOM도 Radix 인스턴스도 통째로 사라진다.** 보는 범위를 좁히는 것이
곧 성능 대책이다.

> 단, 래퍼 컴포넌트 자체는 마운트되어 훅을 돈 뒤 `null`을 반환한다. **비용의 대부분이
> 사라지는 것이지 전부는 아니다.** 이 설계는 "가벼워진다"까지만 약속한다.

## 이미 있는 것

새로 만들 것을 고르기 전에, 이 기능의 8할은 이미 리포 안에 흩어져 있다.

| 있는 것 | 위치 | 한계 |
|---|---|---|
| `?hidden=` | `userEditing/Provider.tsx` | 압축돼 URL에 영속. `from-link`도 아는 형식 |
| `updateNodesHiddenState` | `ERDContent/utils/` | 노드에 `hidden` 세팅 |
| `extractSchemaForTable` | `TableDetail/` | **1 hop 고정.** 깊이 개념이 없다 |
| `handleOpenMainPane` | `TableDetail.tsx` | 실질적으로 1-hop 포커스. 아래 3가지가 문제 |
| 테이블별 hide / Hide All | 사이드바 | 하나씩. 관계를 모른다 |
| 커맨드 팔레트 | `CommandPalette/` | 이름 검색은 이미 된다 — 텍스트 필터를 또 만들 이유가 없다 |

`handleOpenMainPane`의 문제 셋:

1. **드로어의 "Related tables" 섹션 안에 묻혀 있다.** 이런 기능이 있다는 것을 알 수 없다.
2. **깊이가 없고 돌아갈 길이 없다.** 한 번 누르면 나머지가 사라지고, 되돌리려면 URL을 손대야
   한다.
3. **`computeAutoLayout`을 다시 돌려 `setNodes`한다.** `layout.json`으로 손수 맞춰둔 배치가
   포커스 한 번에 화면에서 무너진다.

## 결정

| 질문 | 결정 | 근거 |
|---|---|---|
| 포커스를 URL에 어떻게 남기나 | **규칙으로.** `?focus=<table>:<depth>` | 스키마 크기와 무관하게 URL이 짧고, 나중에 링크를 열었을 때 **의도가 남는다**("users에서 2홉"). 계산 결과를 `?hidden=`에 펼쳐 넣으면 왜 숨겨졌는지 알 수 없고, 스키마가 바뀌면 조용히 어긋난다 |
| 진입 시 재배치하나 | **안 한다. `fitView`만** | 큐레이션한 `layout.json`을 포커스가 무너뜨리면 안 된다. 재배치가 필요하면 툴바의 `Tidy up`이 이미 있다 — 이것이 "포커스는 절대 배치를 건드리지 않는다"를 안전하게 만드는 근거 |
| 저장된 뷰(`views.json`) | **안 만든다** | 새 사이드카 + CLI 표면 + UI. 기능 과잉 |
| 텍스트 필터 | **안 만든다** | 커맨드 팔레트가 이미 이름 검색을 한다 |

## 동작

### 규칙

```
?focus=users:2
```

- **hop = FK 한 개, 방향 무시.** `depth 1` = 직접 이웃.
- **깊이 상한 3.** 그 이상은 대부분의 실무 스키마가 전부 연결돼 있어 "전체 보기"와 같아진다.
- 관계가 하나도 없는 테이블에 포커스하면 그 테이블 하나만 남는다.
- 파라미터가 없거나 대상 테이블이 스키마에 없으면 **포커스는 없던 것으로 친다** — 스키마가
  바뀌어 이름이 사라져도 빈 화면이 되지 않는다.

### `?hidden=` 과의 합성

한 줄로 정한다.

> **`?focus=`가 보일 집합을 정하고, `?hidden=`이 거기서 뺀다.**

- 포커스 중에 테이블을 숨기면 `?hidden=`에 더해진다. 둘은 독립적으로 살아남는다.
- **"다시 추가"는 만들지 않는다.** 더 보려면 깊이를 올리거나 포커스를 푼다. 규칙이 한 방향일
  때만 "지금 왜 이게 안 보이지"에 답할 수 있다.

### 진입점

1. 테이블 우클릭 메뉴에 `Focus` — 편집 모드 밖에서도 동작해야 한다(읽기 전용 링크를 받은
   사람이 가장 필요로 하는 기능이다).
2. 기존 "Related tables → open main pane" 버튼을 **이 경로로 갈아끼운다.** 같은 일을 하는
   코드가 둘이 되지 않게 한다.

### 되돌아가기

편집 모드 배지와 같은 자리에 배지를 띄운다. 깊이 조절이 곧 배지다.

```
Focused on users · [1] [2] [3] · Show all
```

## 작업 표면

| 파일 | 변경 |
|---|---|
| `stores/userEditing/Provider.tsx` | `?focus=` 쿼리 상태 추가 (`history: 'push'` — 뒤로가기로 포커스가 풀리는 것이 자연스럽다) |
| `features/erd/utils/focus/` (신규) | `tablesWithinDepth(schema, table, depth)` — 순수 함수. BFS. **여기가 테스트 대상** |
| `TableDetail/extractSchemaForTable.ts` | 위 함수로 대체하거나 depth=1 호출로 축소 |
| `ERDContent` | `?focus=` → 보일 집합 계산 → `updateNodesHiddenState`. 재배치 없음 |
| `TableDetail.tsx` | `handleOpenMainPane`의 `computeAutoLayout` 제거 |
| `ErdContent.tsx` 우클릭 메뉴 | `Focus` 항목 |
| 배지 컴포넌트 | 깊이 토글 + `Show all` |

## 검증

- **단위:** `tablesWithinDepth` — depth 0/1/2/3, 순환 참조, 자기참조 FK, 고아 테이블, 없는
  테이블 이름.
- **브라우저 (116테이블 픽스처):**
  - 포커스 후 `.react-flow__node` 개수가 계산된 집합과 일치
  - **포커스 전후로 남은 테이블의 `transform`이 동일** — 재배치가 안 일어났다는 증거
  - `?focus=` 를 단 URL로 새로고침 → 같은 화면
  - `Show all` → 전부 복귀, 위치 그대로
- **성능:** 포커스 전후 `TooltipProvider` 인스턴스 수 / 렌더 시간 비교. **숫자로 남긴다** —
  "가벼워졌다"는 보고는 받지 않는다.

## 범위 밖

저장된 뷰 · 텍스트 필터 · 그룹 단위 포커스 · `onlyRenderVisibleElements`(별건. 측정치 −28%,
그룹 박스 지오메트리 리스크가 있어 아직 보류).

## 열린 질문

- 포커스 중 `Tidy up`을 누르면 보이는 것만 재배치할 텐데, 그 결과를 `?positions=`에 커밋할
  것인가. 커밋하면 포커스를 푼 뒤 배치가 달라져 있다. **구현 중 결정.**
- 배지를 편집 모드 배지와 같은 자리에 두면 둘이 동시에 뜰 때 자리가 겹친다. **구현 중 결정.**
